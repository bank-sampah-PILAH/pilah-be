## API contract

`GET /api/v1/aktivitas` requires an active pengelola and uses their current bank.
It combines setoran and pencairan, filters before SQL pagination, and orders by
descending transaction date, creation timestamp, type and ID. The final keys
make ordering deterministic when timestamps match.

Parameters:

- `periode`: `semua` (default), `hari_ini`, `minggu_ini`, `bulan_ini`,
  `bulan_lalu`, `1_bulan`, `3_bulan`, `6_bulan`, `12_bulan`, `custom`.
- `tipe`: `semua` (default), `setoran`, `pencairan`.
- Custom dates: `dari_tanggal` and `sampai_tanggal`, ISO dates, inclusive in the
  configured local timezone. Reversed dates return 400; missing/invalid filter
  values return 422.
- `search`: nasabah name, case-insensitive, applied before pagination.
- `page`, `page_size`: standard pagination, page size capped at 100.

Rolling month periods subtract calendar months from today, clamp the day to
the target month's last day, and include today. They differ from `bulan_lalu`,
which selects the complete previous calendar month.

Response: `{count, next, previous, results}`. Each result is
`{tipe: "setoran" | "pencairan", data: <existing typed transaction DTO>}`.
Detail objects are fetched only for the current page.

The shared ledger query is exposed through `apps.ledger.api`. The existing
nasabah history endpoint can opt into the combined query with explicit `tipe`,
while keeping membership isolation and its small `{id, tanggal, tipe,
total_nilai}` DTO. Requests without `tipe` retain their PIL-315 behavior.
PIL-248 can reuse the filter query for summaries and export; XLSX expansion is
outside this issue.
